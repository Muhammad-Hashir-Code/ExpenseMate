1. Introduction
1.1 Purpose
This document specifies the functional and non-functional requirements for ExpenseMate, a personal expense management system. It is intended for the development team, course instructor, and evaluators as the baseline for design, construction, and testing in subsequent assignment phases.
1.2 Scope
ExpenseMate is a local client-server desktop application that enables a single user to record income and expenses, set monthly category-wise budgets, receive budget alerts, import/export transaction data as CSV, and view visual analytics (charts) of spending. The system will be implemented using Python with an SQLite database. Multi-currency support and cloud backup are out of scope for the initial release and are planned as adaptive maintenance features.

2. Overall Description
2.1 Product Perspective
ExpenseMate is a new, standalone system with a local client-server architecture: a lightweight UI client communicates with a backend logic/data layer that persists records in an SQLite database on the same machine.
2.2 Product Functions (Summary)
Record and categorize income and expense transactions
Define and track monthly budgets per category
Trigger budget alerts when spending thresholds are reached
Import/export transactions via CSV
Display category-wise analytics through visual charts
Generate period summary reports
2.3 User Classes and Characteristics
Primary user: an individual managing personal finances, with basic computer literacy and no programming background. The system is designed for single-user, non-administrative use in this release.
2.4 Operating Environment
Desktop environment (Windows/Linux/macOS) with Python 3.x runtime and local SQLite database file; no external network dependency required for core functionality.
2.5 Design and Implementation Constraints
Must use Python + SQLite (or equivalent C# + SQL stack) as specified by the assignment.
Must follow a layered/client-server architecture separating UI, business logic, and data access.
Development and delivery timeline is bound by the six assignment phases and the 18 Sep 2026 deadline.
2.6 Assumptions and Dependencies
The user has the application installed locally; no multi-user concurrency is assumed.
CSV files used for import follow a defined column format (date, amount, category, description).
Charting relies on a Python charting library (e.g., Matplotlib) available in the runtime environment.

3.2 Non-Functional Requirements
ID
Category
Requirement Description
NFR-1
Performance
The system shall load the dashboard and render charts for up to 5,000 transactions within 2 seconds.
NFR-2
Usability
The UI shall allow a new user to record a transaction in no more than 3 clicks/steps.
NFR-3
Reliability
The system shall not lose recorded data in the event of an application crash (transaction-safe DB writes).
NFR-4
Portability
The client-server components shall run on Windows, Linux, and macOS without code changes.
NFR-5
Security
User passwords shall be stored using a salted hash; the local database shall not store passwords in plain text.
NFR-6
Maintainability
The codebase shall follow a layered structure (UI / Logic / Data) with unit test coverage ≥ 70% per module.
NFR-7
Scalability
The database schema shall support extension to multi-currency and cloud backup without redesign.
